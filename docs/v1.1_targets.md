# v1.1.0 Targets — falsifiable claims for the rewrite loop

**Status (2026-07-12): not yet met. This document records the
benchmarks the rewrite loop must satisfy before v1.1.0 can be
tagged. All four assertions are loose — once the loop is implemented
and a recorded run produces real numbers, those numbers become the
realistic SLOs in `SLO.md`.**

## Why a targets document before the implementation

The architecture's central claim is:

```
generate → verify → diagnose → repair → verify again
```

Without the `repair → verify again` loop, only the first half of
the claim is testable. v1.1.0 must close the loop *and* prove the
closed loop improves the benchmark.

A benchmark run that records metrics but does not assert against
them is not a falsifiable benchmark. This document fixes the
assertion surface before any code is written, so the implementation
can be evaluated against a fixed target rather than moving goalposts.

## The four assertions

Each is asserted by the live integration test
`code2testbench/tests/integration/test_failure_mode_corpus.py`
when `OPENAI_API_KEY` is set. The test is `pytest.skip`'d otherwise
because it requires the configured LLM provider.

| Assertion | Threshold | Meaning |
|-----------|-----------|---------|
| `diagnosis_trigger_rate == 1.0` | exact | For every failed test in the failure-mode corpus, the diagnosis_agent fires. (Already true at `59894d6`.) |
| `rewrite_attempt_rate == 1.0` | exact | For every failed component, exactly one rewrite attempt is recorded. Per-component invariant, not per-run. |
| `rewrite_success_rate > 0.0` | floor | At least one rewrite produces a passing test. (Loose: we want *some* signal of working rewrites, not aspirational success counts.) |
| `final_acceptance_rate > initial_acceptance_rate` | floor | After rewrites, more tests pass than before rewrites. The project's central claim. |

Higher thresholds are deliberately deferred. The first recorded
run produces the realistic SLOs.

## Recorded-vs-aspirational discipline

A common failure mode for benchmark projects is to set targets
that look impressive but aren't grounded in measured performance.
The discipline here is the opposite direction: targets start loose
and tighten only after measurement. This means the first v1.1.0
release ships with thresholds that may be too generous; v1.2 then
tightens them based on real performance, not guesses.

## Why per-component, not per-run

If the rewrite cap were per-run, the benchmark would be sensitive
to corpus ordering: one early failure could prevent every later
component from exercising the rewrite path. Per-component caps
guarantee every component gets the same treatment, making the
benchmark reproducible across orderings.

## Why exactly-one rewrite per component

A single rewrite measures whether the system can self-correct
once. A second attempt would measure whether it can iterate —
useful research, but expensive in LLM cost and unlikely to produce
data the first attempt didn't. Two attempts per component would
double runtime for marginal additional signal. One attempt is the
default; multi-pass retry is a v1.2 question.

## Why full-suite re-run after every rewrite

A rewrite that makes the failing test pass but breaks another test
should not count as success. Re-running the entire suite after
every successful rewrite is what makes the metric honest. The
`final_acceptance_rate` denominator counts rewrites whose
post-suite outcome was "more tests passing than before"; the
numerator counts those.

## Six fields per rewrite, recorded

Every `RewriteAttempted` event carries:

| Field | Type | Source |
|-------|------|--------|
| `run_id` | str | Generator-level id for the benchmark run |
| `component_id` | str | Which component was rewritten |
| `failure_id` | str | Which test case triggered the rewrite |
| `failure_classification` | str | The diagnosis agent's `cause` value: `TEST_WRONG`, `CODE_BUG`, or `INTENT_WRONG` |
| `strategy` | str | The rewrite strategy: `test_rewrite`, `intent_rewrite`, or `skip` |
| `success` | bool | Whether the rewrite produced a passing test |
| `elapsed_seconds` | float | Wall-clock time of the rewrite attempt |

These fields give us the data to understand *why* a benchmark
improved or didn't. `strategy == "skip"` with `cause == CODE_BUG`
means the diagnosis correctly classified the failure as a source
bug; `strategy == "test_rewrite"` with `success == False` means the
test rewrite failed to produce a passing test. Without these
fields, the aggregate numbers can't be explained.

## Two metrics, not one

`final_acceptance_rate` and `rewrite_success_rate` measure
different things:

- `rewrite_success_rate` is the per-event metric: of all
  rewrites attempted, what fraction produced a passing test.
- `final_acceptance_rate` is the per-run metric: after all
  rewrites in the run, what fraction of rewritten components
  have at least one passing test.

Both go in `AcceptanceReport.to_dict()`. Both are recorded in
the benchmark JSON. v1.2 may tighten thresholds on each
independently.

## The recorded JSON shape

`latest_report_failure_modes.json` after v1.1.0 lands will have:

```json
{
  "schema_version": 2,
  "provider": "openai",
  "model": "MiniMax-M3",
  "confidence": 0.0,
  "initial_acceptance_rate": 1.0,
  "diagnosis_trigger_rate": 1.0,
  "rewrite_attempt_rate": 1.0,
  "rewrite_success_rate": <first measured value>,
  "final_acceptance_rate": <first measured value>,
  "net_improvement": <first measured value>,
  "_num_components": 1,
  "_rewrite_events": [
    {
      "component_id": "validators",
      "failure_id": "test_is_valid_email_rejects_at_only_no_dot",
      "failure_classification": "TEST_WRONG",
      "strategy": "test_rewrite",
      "success": <bool>,
      "elapsed_seconds": <float>
    }
  ]
}
```

The `_rewrite_events` array is the per-event data; the four
metrics are the aggregate. Both are required for v1.1.0 to be
considered falsifiable.

## What this document is NOT

This is not an SLO. SLOs come from measured numbers; this
document is the assertion surface that produces them. Once v1.1.0
is recorded and the four assertions hold, the measured numbers
go into `SLO.md` and this document is updated to reference them.
